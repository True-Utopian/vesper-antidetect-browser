# Local desktop upgrade identity

The actual Browser 0.3.0 → 0.4.0 and Workbench add-on 0.4.0 → 0.5.0 upgrade on this PC exposed a persisted coordinator identity bug. Windows MSIX resolves the logical roaming data directory to its physical package-local cache directory. Browser profiles and the node-id file were preserved, but Workbench derived a different tenant and quota key from the new path spelling. The existing globally unique node workspace key then rejected registration with `engine_nodes_workspace_key_key`.

The finding was verified on a disposable copy of the checksum-verified offline database backup. Its single engine node matched the persisted node-id and the previous logical-path tenant, rather than the new physical-path tenant. No live database rows were edited.

Workbench 0.5.1 resolves local identity from the owned database and persists `coordinator/identity.json`. Existing node, tenant, quota, and team records are retained. Migration validates UUIDs, the node's workspace key, the derived quota identifier, and the physical Browser store behind a default local team key. A saved identity must agree with the database; explicit conflicting configuration, a different Browser store, and ambiguous records are rejected. New workspaces use the physical Browser directory. Remote PostgreSQL coordination retains its existing configuration behavior.

Workbench 0.5.2 also initializes the embedded Browser store before resolving identity, allowing a fresh local coordinator to start before any browser executable is installed. Empty environment settings continue to mean unset. A regression launches the actual CLI twice against a fresh isolated store and verifies stable identity and released database ownership without launching a native profile.

The upgrade helper defaults to read-only preflight. Applying an update requires stopped desktop apps and service owners, no profile leases or live native profile PIDs, no enabled schedules, and no unfinished runs. It copies the complete private store to a new sibling backup, verifies every file checksum, and checks managed-flow activity only on a disposable database clone. Add-on installation uses a verified signed package, a new version directory, and an atomic registry replacement; original files remain byte-identical except the intended registry change. Prior enablement is retained. The interactive Browser is launched visibly with its explicit existing physical data directory.

Spawn success is not startup qualification. Post-upgrade checks must confirm a visible application window and authenticated Browser and Workbench API versions, readiness, and shared Browser endpoint. Saved reports are private under `test-results/native-engine`; they contain no access tokens. Local Ed25519 artifact verification is distinct from Windows Authenticode publisher signing.
