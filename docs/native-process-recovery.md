# Native process interruption

Original Vesper behavior and qualification by **true-utopian**, 13 October 2026.

The actual Browser 0.4.7 / Workbench 0.5.9 installation passed an owned native-process interruption fixture. The test verified the exact executable and physical profile path before interrupting only its new browser process. Browser refused the dead connection; explicit Workbench cancellation confirmed stop and released the profile lease. Reopening that same profile retained committed localStorage, IndexedDB and native CPU/memory settings. Original profile metadata and idle leases were preserved. These five checks qualify explicit recovery of that fixture.

A separate earlier interruption, three seconds after a new localStorage write, lost that write while IndexedDB survived. The native Chromium storage implementation batches localStorage commits with a five-second default delay. The committed-data fixture waited until its unique value appeared in the owned storage file before interruption; the observed wait was 4,984 ms. This does not qualify preservation of arbitrary recent writes, OS power loss or the full crash-recovery matrix. The earlier failed receipt is retained privately.

The installed Inspect worker remained in its operator Finish wait after browser loss until explicitly cancelled. The source correction watches its Browser-owned connection throughout automation, aborts pending input/Finish requests on disconnect, and terminates without claiming a save. It removes the watcher on successful completion so intentional final disconnect does not create a false failure. The native kernel itself is unchanged.

Five lifecycle regressions and the complete source suite passed: **196 tests**, zero failures and one optional external PostgreSQL skip. A separate real compiled source worker reached Inspect through the installed native Browser, then terminated 36 ms after the verified owned native process exited. Four source integration checks passed, including preservation of original profile metadata and idle lease state. These source checks preceded the signed 0.5.10 add-on release. The historical 0.5.9 limitation is resolved by the installed follow-up below.

The signed **Workbench 0.5.10** add-on and standalone full installer passed local signatures, a production dependency audit with zero vulnerabilities and nine native cases against the copied installer runtime. Browser 0.4.7 with the new add-on passed 35 packaged checks; the standalone app passed five startup/form/layout checks at 1366 and 1024 window widths. The add-on archive was checked to contain the exact newly compiled worker and lifecycle module. Packaging rejects a stale payload version. Add-on-only upgrades now also bind the signed artifact checksum to its accepted release record.

The guarded actual upgrade made a fresh verified backup of **82,083 files (1,200,880,098 bytes)** and preserved every original byte except the intended add-on registry. It reused the installed Browser and native kernel. Five actual integration checks then passed: native process loss while Inspect waits for Finish automatically failed the run in **328 ms**, confirmed stop, released the lease and made no archive claim. A subsequent normal run saved a checksum-verified **65,852-byte** archive. Six actual UI checks confirmed the visible failed/saved results, ordinary 13-field Inspect form, default form/JSON round trip, readable native-policy descriptions and cancel without submitting a run. The app was left open and idle.
